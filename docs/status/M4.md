# Milestone M4 Status

## Outcome

M4 implements a backend-neutral local LLM adapter, deterministic mock, loopback/subprocess llama.cpp transport, bounded request management, strict structured-output validation and M3 transaction integration. It does not implement Stage 1 or any M5 workflow, download a model, call cloud services or change canonical bytes.

## Design

- Typed request/response, termination and semantic-assessment models isolate backends.
- M1 capsule bytes and digest are accepted without loading the full canonical prompt.
- M2 strict JSON, exact field order, schema version and implementation status gate every structured commit.
- M3 records one generation call per attempt, response lineage, deterministic gate evidence and artifact binding.
- Request/response bodies are not logged; persistence retains digests, model identity, adapter version, duration and termination reason.
- Retry, timeout, cancellation and subprocess cleanup are bounded. There is no cloud adapter or fallback.
- Migration `002_llm_call_metadata.sql` adds generation-call audit metadata with checksum/version handling inherited from M3.

## Local smoke status

`tests/integration/test_llama_cpp_smoke.py` is optional and explicit. It reports SKIP when `AUDIO_STORY_LLAMA_CPP_SMOKE_URL` is absent. M4 makes no claim that llama.cpp or a model is installed.

## Limits

- Token input budgeting uses a deterministic character ceiling; backend-specific tokenizer accounting requires an installed model/backend and remains a capability-probe concern.
- HTTP cancellation can be observed before and after a blocking request; hard process termination applies only to subprocesses owned by the adapter.
- Semantic/model quality is not a deterministic PASS and is not implemented as a Stage workflow.
- `PCF001_STAGE4_AUDIO_MODE_DEFAULT_COLLISION` remains unresolved.
- M4 remains uncommitted for review. M5 has not started.
